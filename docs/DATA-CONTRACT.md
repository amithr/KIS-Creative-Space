# KIS Shared Data Contract (web ⇄ Android app)

Identical copy of this file ships in both handoff packages (`design_handoff_kis_web`, `design_handoff_kis_flutter`). It is the single source of truth for the entities both clients read and write. Backend: one shared realtime database (Supabase or Firestore); prototypes stub it with `localStorage` keys noted below.

## Entities

### Item  — prototype key `kis-inventory-v1`
```
Item {
  id: string            // AUTOGENERATED alphanumeric code, e.g. "KIS-7F3K9Q" ("KIS-" + 6 chars,
                        //   ambiguous glyphs excluded). Immutable; assigned at creation; this exact
                        //   string is what the printed QR label encodes. Never user-editable.
  name: string
  note: string          // short description
  area: "LEGO Play" | "Robotics" | "Art & Design" | "VR Lab" | "3D Printing"
  avail: int            // physical units in the space right now (admin-managed)
  total: int            // owned units; 0 ≤ avail ≤ total
  added: timestamp      // drives the NEW badge / "New this week" filter (7 days)
}
```

### Booking (room schedule) — prototype key `kis-schedule-v1`
```
Booking { date: ISO date, period: 1–8, teacherName: string, createdAt: timestamp }
```

### Reservation — prototype key `kis-reservations-v1`
One record covers reservations AND walk-up loans; status carries the lifecycle.
```
Reservation {
  id: string
  itemId: string
  qty: int                       // units requested
  by: string                     // "Ms. Bondar, 7B"
  days: ISO date[]               // one or more school days, ≤ 7 days ahead
  periods: "all" | [start, end]  // period range 1–8, or whole day
  status: "reserved" | "out" | "returned"
  outQty: int                    // units currently checked out (0 unless status = out)
  source: "web" | "app"          // web = teacher reservation; app = walk-up check-out
  at: timestamp                  // created
  outAt?: timestamp              // last check-out
  returnedAt?: timestamp         // fully returned
}
```

### ActivityEvent — append-only audit feed
```
ActivityEvent {
  type: "reserve" | "checkout" | "checkin" | "add" | "remove" | "edit" | "sync"
  itemId?: string
  reservationId?: string
  actor: string                  // teacher name or "admin"
  source: "WEBSITE" | "THIS PHONE" | "ADMIN" | "AUTO"
  at: timestamp
}
```

## Who writes what
- **Web** creates/cancels `Reservation` (status `reserved`), manages `Item` stock and `Booking`. **Web admin can also check out / check in by typing an item code** (the same alphanumeric `Item.id` from the QR label) — the app resolves it by camera scan, the web by text entry; both produce identical status transitions.
- **App** transitions reservation status: check-out (`reserved → out`, sets `outQty`), check-in (`out → returned` when `outQty` hits 0; partial returns decrement `outQty` and keep status `out`). Walk-up check-outs create a Reservation directly with `status: "out"`, `days: [today]`, `periods: "all"`, `source: "app"`. App also does full Item CRUD.
- Both append `ActivityEvent` for every mutation.

## Availability math (both clients must agree)
- `Item.avail` is physical stock; reservations do NOT decrement it.
- Free units for item *i* on day *d*, period *p*:
  `free(i,d,p) = i.avail − Σ qty of reservations for i whose days include d, whose periods cover p, and whose status ≠ "returned"`
- Web reservation panel: qty cap = min of `free` over the selected days × periods; a period chip is disabled when its `free` is 0 on any selected day.
- Web Resources table shows an amber OUT band under an item while any reservation for it has status `out` ("3 OUT · Checked out to Ms. Bondar, 7B · due back Fri after P8").

## Sync rules
- Optimistic writes with a local offline queue on the app; last-write-wins per field via server timestamps.
- Both clients subscribe to realtime changes on `items`, `reservations`, `activity`; a status change on either side must appear on the other within ~1s when online.
